Finding 2: Guardrail Parallel Hierarchy (~12 types → 4) ​

  • Category: 3B (Consolidation via Generics)
  • Current DX: H=2.0, A=1.5, Combined=1.6
  • Impact: HIGH

Current API (12 types):

swift
// 4 protocols
public protocol InputGuardrail
public protocol OutputGuardrail
public protocol ToolInputGuardrail
public protocol ToolOutputGuardrail

// 4 closure-based (2 deprecated)
public struct ClosureInputGuardrail      // deprecated
public struct ClosureOutputGuardrail     // deprecated
public struct ClosureToolInputGuardrail
public struct ClosureToolOutputGuardrail

// 4 builders
public struct InputGuardrailBuilder
public struct OutputGuardrailBuilder
public struct ToolInputGuardrailBuilder
public struct ToolOutputGuardrailBuilder

Proposed API (4 types):

swift
// Phase marker enums (zero-cost, namespace only)
public enum GuardrailPhase: Sendable {
    public enum Input {}
    public enum Output {}
    public enum ToolInput {}
    public enum ToolOutput {}
}

// One protocol with phase-specific associated validation
public protocol GuardrailProtocol<Phase>: Sendable {
    associatedtype Phase
    var name: String { get }
    func validate(_ context: GuardrailContext<Phase>) async throws -> GuardrailResult
}

// One concrete closure-based type
public struct Guard<Phase>: GuardrailProtocol {
    public init(name: String, handler: @escaping @Sendable (GuardrailContext<Phase>) async throws -> GuardrailResult)
    // Static factories for common guards
    public static func maxLength(_ limit: Int) -> Guard<GuardrailPhase.Input>
    public static func notEmpty() -> Guard<GuardrailPhase.Input>
    public static func custom(_ name: String, _ handler: ...) -> Guard<Phase>
}

// GuardrailResult stays as-is (already clean)
  • Rationale: 12 types doing the same thing for 4 phases. Generics eliminate the parallel hierarchy entirely. An agent sees Guard<.Input> and knows exactly what it is.
  • Breaking: Yes — migration: InputGuardrail → GuardrailProtocol<GuardrailPhase.Input>, InputGuard → Guard<GuardrailPhase.Input>
  • Swift 6.2 Feature: Primary associated types, phantom type markers
  • Effort: Medium (2-4 hours)

Finding 3: LLM Provider Config Types Should Be Internal (~9 types) ​

  • Category: 3A (Access Control Tightening)
  • Current DX: H=3.0, A=2.5, Combined=2.6
  • Impact: HIGH

Current: Users must navigate LLM.OpenAIConfig, LLM.AnthropicConfig, LLM.OpenRouterConfig, LLM.AdvancedOptions, LLM.OpenRouterOptions, LLM.OllamaConfig, OllamaSettings, OpenRouterRouting, OpenRouterRouting.Provider, OpenRouterRouting.DataCollection

Proposed: Config types become internal. Factory methods take simple params:

swift
// BEFORE
let provider = LLM.anthropic(apiKey: "sk-...", config: AnthropicConfig(model: "claude-4", baseURL: nil, apiVersion: nil))

// AFTER — config is internal, factory uses labeled params
let provider = LLM.anthropic(key: "sk-...", model: "claude-4")
let provider = LLM.ollama("mistral")  // already clean
  • Breaking: Low — factory methods already exist; just hide the config structs
  • Effort: Low (1 hour)
